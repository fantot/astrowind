“帮我把网站手机端优化一下。”

这句话交给 GPT-6 Astra，它可能真的会改好手机端，也可能顺手换掉导航结构、重写组件、升级依赖，最后桌面端反而出现新问题。模型不是故意乱改，它只是把“优化”理解成了可以自由发挥。

AI 编程最实用的技巧，不是写一条更长的提示词，而是把工作变成一套有边界的工程流程：先看现状，再做最小修改，最后用命令和差异验收。下面用一个 Astro 网站的真实小需求演示：知识库卡片在手机上图片过高，希望保持现有桌面布局，只调整小屏显示。

## 动手前，先把现场留住

无论在 Codex、其他代码 Agent，还是普通 ChatGPT 里协作，先做三件事：

1. 确认项目现在能正常运行；
2. 查看 Git 是否已有未提交修改；
3. 记录修改前的页面截图或复现步骤。

本地项目可以先执行：

```bash
git status --short
npm run build
```

如果构建原本就失败，要把错误记录下来。否则修改结束后，你无法判断错误是这次产生的，还是之前就存在。

看到未提交文件时，不要直接让模型“清理工作区”。这些内容可能是你还没提交的工作。正确做法是告诉它：现有改动属于用户，只能绕开，不能覆盖、回退或一起提交。

## 第一张任务卡：把需求写到可以验收

一个合格的代码任务，至少包含六项：目标、现象、环境、允许修改、禁止修改、验收标准。

```text
任务：修复知识库列表在手机端图片过高的问题。

现象：
- 页面：/blog
- 屏幕宽度约 390px 时，文章图片占据过多首屏高度；
- 桌面端当前布局正常，不需要重新设计。

技术环境：Astro 7、Tailwind CSS 4、TypeScript。

允许修改：
- 知识库列表卡片组件；
- 与该组件直接相关的样式。

不要修改：
- 文章内容和路由；
- 全局配色、字体和导航；
- package.json 与依赖版本；
- 其他未提交文件。

验收标准：
1. 390px 宽度下图片完整铺满容器，不出现灰色空白；
2. 图片可以裁切，但不能拉伸变形；
3. 桌面端维持现有图文两栏和图片比例；
4. npm run build 通过；
5. 最终列出修改文件和测试结果。
```

这张卡不需要堆“你是世界顶级工程师”之类的角色词。真正能限制结果的，是哪些地方能动、哪些地方不能动，以及怎样算完成。

## 第一步只允许检查，不允许写代码

让 GPT-6 先找到渲染链路：路由用了哪个列表组件，组件怎样传图，图片最终由哪个公共组件输出，当前 CSS 为什么会留下空白。

```text
先只检查，不修改文件。

请完成：
1. 找到 /blog 对应的页面、列表组件和图片组件；
2. 说明图片宽高由哪些属性或 class 控制；
3. 判断空白来自固定高度、图片比例、object-fit，还是父容器布局；
4. 给出最小修改方案和预计涉及的文件；
5. 说明该方案可能影响哪些页面。

检查完成后暂停，等待我确认方案。
```

这一步很关键。很多“改了又改”的根源，是模型还没找准负责渲染的组件，就先在页面外层叠样式。看起来短期有效，换个屏幕宽度又坏了。

## 只批准最小方案，不批准顺手重构

假设它发现问题来自图片容器固定高度，而图片本身用了 `object-contain`，最小方案可能是：保留容器比例，改成 `object-cover`，并只在手机断点调整高度。

这时可以回复：

```text
采用最小方案。只修改你刚才列出的组件，不重构公共图片系统，不升级依赖。

修改后依次执行：
1. 查看 git diff，确认没有无关文件；
2. 运行项目已有的格式检查；
3. 运行 npm run build；
4. 汇报实际结果，不要只写“理论上可行”。

如果发现需要扩大修改范围，先停下来说明原因。
```

“如果要扩大范围先停下”非常有用。它把模型从自由施工的承包商，变成需要变更确认的协作者。

## 报错时，不要把整段日志反复丢进去

构建失败后，可以让 GPT-6 读日志，但要它先分类：

- 这次改动直接引起；
- 环境或依赖引起；
- 修改前已经存在；
- 目前证据不足。

提示词：

```text
构建失败。先不要连续尝试不同修复。

请读取错误日志并回答：
1. 第一个真正导致失败的错误是什么；
2. 它对应哪个文件、哪一行或哪个依赖；
3. 是否与本次 diff 有直接关系；
4. 最小修复是什么；
5. 修复后用什么命令证明问题已解决。

忽略由第一个错误连带产生的重复报错。
```

判断“第一个真正的错误”比盯着最后一行重要。很多日志最后写的是 `build failed`，原因其实在上面几十行。

## 用三层验收，不要只看模型说“完成了”

### 第一层：命令验收

至少运行项目自己的检查和构建命令。AstroWind 这类项目常见的是：

```bash
npm run check
npm run build
```

有单元测试、端到端测试时，也应执行对应命令。测试失败就记录真实失败项，不能把“命令已运行”写成“测试已通过”。

### 第二层：差异验收

执行：

```bash
git diff --stat
git diff
```

重点看：

- 是否出现需求之外的文件；
- 是否改了依赖和锁文件；
- 是否删除了原有功能；
- 是否把临时日志、截图或测试文件留进仓库；
- 同一个问题是否用了多处重复样式修补。

### 第三层：页面验收

至少检查手机和桌面两种尺寸，不能只缩窄浏览器看一眼。建议覆盖：

- 390px 左右的手机宽度；
- 768px 左右的平板断点；
- 1440px 左右的桌面宽度；
- 有图片和无图片的文章；
- 标题一行和标题三行的卡片；
- 浅色模式，以及网站确实提供时的深色模式。

视觉问题最终要用页面判断，构建成功只能证明代码可以生成，不能证明图片没有变形。

## 一份适合 Codex 的完整任务模板

以后让 GPT-6 改代码，可以直接复制下面这份，再替换方括号内容：

```text
目标：
[一句话写清最终变化]

复现：
1. 打开 [页面或功能]
2. 执行 [操作]
3. 当前看到 [错误现象]
4. 期望看到 [正确结果]

环境：
[框架、版本、运行命令]

边界：
- 可以修改：[文件或模块]
- 不要修改：[路由、数据、依赖、样式等]
- 保留现有未提交改动，不覆盖、不回退；
- 不创建与任务无关的临时文件。

工作方式：
1. 先检查代码并解释原因，不立即修改；
2. 给出最小方案和影响范围；
3. 确认后实施；
4. 运行 [检查命令] 和 [构建/测试命令]；
5. 查看最终 diff，删除无关改动；
6. 汇报修改文件、测试结果和剩余风险。

验收标准：
- [可以观察或测量的标准 1]
- [标准 2]
- [标准 3]
```

## 哪些操作一定要留给人确认

即使模型可以操作终端，下面几类动作也不建议默认授权：

- 删除文件或大批量覆盖数据；
- 修改生产环境配置；
- 使用密钥、令牌和账号密码；
- 发送邮件、发布内容或提交付款；
- 推送代码、合并分支和部署上线；
- 数据库迁移及不可逆操作。

先让它生成计划和命令，由人确认目标，再执行。效率慢几分钟，总比恢复生产数据快得多。

OpenAI 的官方编程提示建议里，重点同样是明确职责、规范工具使用，并要求充分测试和验证。GPT-6 Astra 能完成更长的工程任务，不代表可以省掉工程纪律。恰恰相反，模型能改的文件越多，任务边界、构建检查和最终 diff 就越重要。
