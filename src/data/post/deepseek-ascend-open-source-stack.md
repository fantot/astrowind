一个模型宣布“支持某款芯片”，和这个模型能够在那款芯片上稳定、快速、低成本地运行，中间隔着很长一段路。

模型权重只是起点。真正决定训练和推理效率的，还有矩阵乘法算子、注意力内核、专家路由、跨卡通信、编译工具以及故障恢复机制。过去讨论国产算力时，大家经常把注意力集中在芯片参数上，却忽略了最费时间、也最容易形成壁垒的软件栈。

2026 年 9 月 30 日，DeepSeek 面向华为昇腾平台开放一批基础组件，包括用于矩阵计算的 **DeepGEMM Ascend**、面向专家并行通信的 **DeepEP Ascend**，以及与内核编译、注意力和稀疏选择有关的 DeepJIT、TileKernels、FlashMLA、DeepSelect 等项目。

这次开源值得关注的地方，不是“DeepSeek 又发了几个仓库”，而是国产算力开始从“能适配模型”，走向“有人公开打磨底层工具链”。

> 本文依据 DeepSeek 官方 GitHub 仓库在 2026 年 9 月 30 日公开的信息整理。项目更新很快，支持的硬件、CANN 版本和性能数据以各仓库最新说明为准。

## 先把这些名字翻译成人话

第一次看到这一串项目名，很容易被术语劝退。它们分别处理的，其实是大模型运行过程中几个很具体的问题。

### DeepGEMM Ascend：让大量矩阵乘法跑得更快

大模型训练和推理中有大量矩阵乘法。GEMM 可以理解为这类计算的核心积木。芯片理论算力再高，如果矩阵计算内核不能把硬件喂饱，实际速度依然上不去。

DeepGEMM Ascend 是 DeepSeek 针对昇腾 NPU 开放的矩阵乘法内核库。它对应的是此前在英伟达 CUDA 平台上的 DeepGEMM，但并不是把代码改个设备名就结束，而是需要重新利用昇腾的计算单元、内存层级和编译环境。

### DeepEP Ascend：解决多张卡之间“搬数据”的问题

DeepSeek 模型大量使用混合专家架构，也就是常说的 MoE。一次推理不会让所有专家都参与，而是把不同 token 分发给不同专家。专家分布在不同加速卡上时，数据需要在卡之间快速交换。

DeepEP Ascend 提供 dispatch、combine 等专家并行通信能力。简单说，它要完成三件事：

1. 判断数据该送到哪张卡上的哪个专家；
2. 尽快把数据送过去；
3. 计算完成后，再把结果正确收回来。

这个环节如果效率不高，多卡集群就会出现“计算单元在等网络”的情况。买了更多卡，性能却没有按比例增长。

DeepSeek 公布的 README 显示，DeepEP Ascend 在昇腾 950DT 测试环境中，部分 dispatch 场景达到了理论有效载荷带宽的约 90% 至 95%。这个数字很亮眼，但必须连同测试条件一起看：它针对特定硬件、CANN 版本、消息大小和并行规模，并不代表所有模型、所有集群都能直接获得同样结果。

### DeepJIT、TileKernels：减少手写底层算子的成本

高性能算子通常要贴近硬件编写，开发门槛高，调试也慢。DeepJIT 和 TileLang、TileKernels 这类工具的作用，是让开发者用更高层的方式描述计算，再针对不同加速器完成编译和优化。

如果这套工具成熟，开发团队不必为每个新算子都从最底层开始写代码。它带来的价值不只是“快”，还包括更短的开发周期、更容易复现的优化过程，以及更低的硬件迁移成本。

### FlashMLA、DeepSelect：把注意力和稀疏选择做成专用内核

FlashMLA 面向多头潜在注意力计算，DeepSelect 则处理 Top-K 选择等场景。后者在 DeepSeek Sparse Attention、采样和专家选择中都会用到。

这些模块看起来很细，但大模型性能往往就是被几十个这样的热点算子决定的。只把通用框架搬到新硬件上，模型也许能运行；把这些关键内核逐个优化，才可能真正接近硬件上限。

## 为什么这比“某模型已适配昇腾”更重要

过去不少国产算力项目的问题，不是完全跑不起来，而是遇到新模型、新算子或大规模集群后，优化过程过度依赖少数厂商工程师。项目能上线，但难以复制；能完成演示，但维护成本很高。

公开底层组件至少带来三点变化。

第一，**优化方法变得可见**。开发者可以看到算子如何组织、通信如何安排、性能数据如何测，而不是只得到一个封装好的二进制文件。

第二，**模型团队可以把昇腾当作一等平台**。如果同一套 API 设计能够覆盖英伟达和昇腾，模型侧迁移不必重写大量上层逻辑。DeepEP Ascend 公开说明中就强调，其 Buffer API 尽量与英伟达版本对齐。

第三，**企业有机会降低单一平台依赖**。这不代表可以立刻无成本换卡，而是未来采购和部署时，多了一条能够验证、能够持续优化的路线。

真正的生态从来不只是一块芯片。编译器、算子库、通信库、框架适配、监控工具、文档和工程人才加在一起，才决定硬件是不是“好用”。

## 现在能不能把生产环境直接迁过去

不建议只看发布消息就做决定。

DeepEP Ascend 当前公开测试主要基于昇腾 950DT 和特定版本的软件栈，部分能力仍标注为开发中或实验状态。开源仓库刚发布时，接口、兼容范围和性能都可能快速变化。它证明了路线可行，但还不能替代真实业务验收。

如果公司正在评估昇腾部署，至少完成下面六组测试。

### 1. 先确认支持矩阵

把硬件型号、CANN 版本、PyTorch 或 MindSpore 版本、驱动、固件、容器镜像逐项记录。不要只写“昇腾环境”，因为同一套代码在不同代际硬件上的结果可能完全不同。

### 2. 用自己的输入长度和并发量测试

官方数据常常针对某些固定尺寸。实际业务要分别测：

- 短问答的首 token 延迟；
- 长文档输入的预填充速度；
- 多用户并发下的吞吐；
- 长输出时的稳定速度；
- 峰值显存和内存占用。

一个模型在单请求上很快，不代表在 100 个并发请求下仍然稳定。

### 3. 多卡测试不能只看平均值

记录 P50、P95 和 P99 延迟，同时观察通信等待时间、掉卡恢复和长时间运行后的错误率。MoE 模型尤其要检查不同专家负载是否均衡，以及并行规模扩大后性能是否还在增长。

### 4. 先做结果一致性，再谈速度

换算子库后，要用一组固定问题比较输出质量。重点检查数值精度、长文本稳定性、工具调用参数和结构化输出，避免为了吞吐提升牺牲正确率。

### 5. 算清完整成本

不要只比较单卡价格。把服务器、网络、存储、电力、机房、运维、工程适配时间和备件都列进来，再计算每百万 token 的实际成本。

### 6. 准备可以退回的方案

新工具链上线初期，保留旧平台镜像、模型版本和回滚脚本。生产环境最怕的不是性能少 10%，而是出现问题后无法快速恢复服务。

## 对普通 AI 用户有什么影响

这次开源不会让手机上的 DeepSeek 第二天突然变快，也不意味着模型会员价格马上下降。它更像是在铺路。

如果国产加速器上的训练和推理效率持续提高，云厂商可用算力会更多，模型服务对单一硬件供应链的依赖会下降。长期看，可能体现在更稳定的服务、更丰富的部署选择，以及更有竞争力的 API 价格上。

对正在学习 AI 的人，这件事也给出一个很明确的方向：只会调用模型 API 已经不够。懂一点算子、显存、并行和通信，会越来越有价值。你不一定要去写底层内核，但至少要能判断性能瓶颈发生在哪一层。

DeepSeek 这次真正打开的，不只是几个代码仓库，而是一条可以被更多工程师看见、验证和继续改进的国产算力路径。它距离成熟商业生态还有路要走，但比一句“已经完成适配”更接近真正的问题。
