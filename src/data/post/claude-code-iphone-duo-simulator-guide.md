AI 编程工具以前最擅长的是“把代码改出来”，最薄弱的是“亲眼看见改完以后发生了什么”。

它可以告诉你 SwiftUI 布局应该自适应，却不知道按钮在真机尺寸下被键盘挡住；它可以补一段尺寸变化处理，却没有验证应用从小屏切到大屏时，用户正在填写的内容是否丢失。

Claude Code 桌面版新加入的 iPhone Duo 模拟器控制，开始补上这段缺口。应用可以与对话并排显示，Claude 不仅能构建和启动项目，还能把模拟设备切换到闭合、半开和展开姿态，观察两种屏幕布局以及折叠过程中的变化，再根据实际结果修改代码。

这项功能目前属于公开测试阶段。它不是“让 AI 一句话替你发布 App”，但已经能把一段过去需要开发者反复手动完成的流程串起来：

```text
阅读代码 → 构建应用 → 启动模拟器 → 改变设备姿态
→ 观察布局 → 定位问题 → 修改代码 → 再次验证
```

下面按一次真实测试的顺序操作。

## 先确认环境，缺一个版本都可能看不到 Duo

测试 iPhone Duo 需要：

- 一台 Mac；
- Claude Desktop **4.29.0 或更高版本**；
- Xcode **27.1 或更高版本**；
- 与 Xcode 对应的 iOS 模拟器运行时。使用 Xcode 27.1 时，需要 iOS 27.1 runtime；
- 一个能够先在 Xcode 中正常编译的 iOS 项目。

普通 iOS 模拟器面板所需的 Claude Desktop 版本门槛更低，但 iPhone Duo 支持要求 4.29.0 以上。更新后要彻底退出并重新启动 Claude Desktop，否则可能仍加载旧组件。

如果 Xcode 没有 iOS 27.1 runtime，打开：

```text
Xcode → Settings → Components
```

下载对应模拟器组件。电脑同时安装多个 Xcode 时，还要确认 Claude 使用的是 27.1 以上版本，而不是系统里另一份旧 Xcode。

建议先在 Xcode 里手动构建一次项目。这样可以提前解决签名、依赖、Scheme 和最低系统版本问题，不要把环境故障和界面问题一次性丢给 Claude。

## 第一次运行：先让 Claude 只检查，不要急着改

打开 Claude Desktop 的 Code 工作区，选择项目目录。第一条指令不要写“适配 iPhone Duo”，因为范围太大，Claude 很容易一边猜问题一边改代码。

先复制下面这段：

```text
请先不要修改代码。

在 iPhone Duo 模拟器中构建并运行当前应用，检查首页在以下状态的表现：
1. Closed（闭合）
2. Half open（半开）
3. Open（展开）
4. Open 状态横屏

每个状态记录：
- 是否能完整显示主要内容
- 是否有控件越界、遮挡或触摸区域过小
- 状态切换后页面位置、输入内容和选择状态是否保留
- 键盘、弹窗、底部栏和安全区域是否正常

先给我问题清单、复现步骤和建议修改文件，不要直接编辑。
```

第一次控制设备时，Claude 会请求相应权限。对具体设备的控制需要用户同意。设备菜单里如果没有 iPhone Duo，在设备列表末尾选择 **Add simulator…**，再添加对应机型。

Claude 在做 Duo 布局检查前，还可能询问是否把 Xcode 自带的 Agent Skills 导出到个人 skills 文件夹。这些技能包含 Apple 提供给编程代理的布局知识。看清目标目录后可以允许，但团队电脑最好先确认公司对个人技能目录的管理规则。

## 怎样控制折叠姿态

模拟器面板中，旋转按钮旁边会出现三个姿态按钮：

- **Closed**：闭合；
- **Half open**：半开；
- **Open**：完全展开。

你可以手动点击，也可以直接告诉 Claude：

```text
把 iPhone Duo 调整到半开 110 度，停留 3 秒后检查当前页面。
```

官方文档说明，半开角度可以在 1 到 179 度之间调整。测试时不必遍历每一度，但建议至少覆盖 45、90、135 度，因为内容跨越铰链、键盘弹出和上下分区常在这些位置暴露问题。

## 第二轮再改代码，而且一次只解决一类问题

拿到问题清单后，不要让 Claude 一次改完所有界面。折叠设备上的布局错误常常互相影响：先改容器尺寸，后面的弹窗问题可能自然消失；一次改十个文件，很难判断哪一步有效。

可以这样继续：

```text
先只修复“Open 状态下详情页内容被铰链分割”的问题。

要求：
- Closed 状态保持现有单栏布局
- Open 状态使用双栏，列表在左、详情在右
- 切换姿态时保留当前选中项和滚动位置
- 不为机型名称写硬编码判断，优先依据可用空间和系统布局信息
- 修改后重新在 Closed、Half open、Open 三种状态验证

完成后列出修改文件、关键原因和验证结果，暂时不要处理其他问题。
```

这段指令有三个好处：范围明确、验收标准明确、要求重新验证。AI 编程最容易出问题的地方，不是不会写代码，而是写完就宣布成功。把“重新运行并观察”写进任务，才能真正利用模拟器能力。

## 一张可以收藏的 Duo 测试清单

只看首页“不崩溃”远远不够。至少检查以下场景：

### 布局

- 闭合时文字和按钮是否被压缩；
- 展开时是否只是把手机版界面粗暴放大；
- 重要内容是否跨过铰链或折痕区域；
- 双栏布局是否存在一边过宽、一边无内容；
- 横屏和半开状态是否出现异常空白。

### 状态连续性

- 折叠前正在编辑的文字是否保留；
- 列表选中项、滚动位置和播放进度是否保留；
- 模态窗口在姿态变化后是否重复出现；
- 网络请求是否因视图重建被重复发送。

### 输入与系统界面

- 软件键盘是否遮挡输入框；
- 焦点在折叠后是否跳到错误控件；
- Sheet、菜单和警告框是否出现在合理屏幕区域；
- 深层链接和通知打开的页面是否正确。

### 无障碍

- 大字体下主要操作是否仍可见；
- VoiceOver 顺序在双栏中是否合理；
- 触摸区域是否至少达到平台建议尺寸；
- 颜色和层级是否依赖折痕才能理解。

### 性能

- 连续折叠、展开是否产生明显卡顿；
- 图片和列表是否在大屏一次加载过多内容；
- 姿态切换是否触发重复初始化或内存增长。

每检查完一个页面，让 Claude 保存截图或写下“姿态、操作、预期、实际结果”。这样第二天再测试时，不需要重新凭记忆判断。

## 一个更完整的自动验收提示词

准备在提交代码前做回归测试，可以直接用下面的模板：

```text
请对当前 iOS 项目做一次 iPhone Duo 回归测试，不要先假设代码正确。

覆盖页面：首页、列表页、详情页、搜索页、设置页。
覆盖姿态：Closed、Half open 90°、Open、Open 横屏。
覆盖操作：启动、切换页面、输入文字、弹出键盘、打开 Sheet、返回、折叠、展开。

验收标准：
1. 无崩溃、无布局越界、无内容被铰链遮挡；
2. 姿态变化后保留输入、选择和滚动状态；
3. 双栏只在空间足够时出现；
4. VoiceOver 顺序与视觉顺序一致；
5. 构建日志中没有新增警告。

请先执行并给出按严重程度排序的测试报告。
只有我确认后，才能修改代码。
每个修复完成后，必须在原复现场景重新验证。
```

不要省略最后三句话。它们能把“发现问题”和“修改代码”分开，也能避免 Claude 为了快速完成任务，顺手改掉你还没有确认的产品行为。

## 模拟器能做什么，不能代替什么

这项能力很适合发现自适应布局、状态恢复、键盘遮挡和基本交互问题，但它仍不能完全代替真机。

真实设备上的铰链手感、屏幕亮度差异、温度、耗电、相机、蜂窝网络、蓝牙和长时间运行表现，模拟器无法完整还原。接近发布时仍要在真实 iPhone Duo 上走一遍核心流程。

另外，公开测试阶段可能遇到姿态不同步、截图失败或坐标不准确。出现异常时先手动切换设备姿态，确认 Xcode 版本和运行时，再判断是不是应用自己的 Bug。不要为了迁就工具故障去改业务代码。

## 隐私和权限别最后才看

Claude 的模拟器功能会让 Agent 看到屏幕内容。Anthropic 文档提示，相关截图可能按照正常对话保留政策发送和保存。因此：

- 不要在被 Claude 控制的模拟器里登录真实个人账号；
- 不要输入生产环境密钥、客户数据和真实支付信息；
- 使用专门的测试账号和假数据；
- 检查构建脚本，避免在本地执行未经确认的命令；
- 团队项目先明确哪些截图和日志可以发送到外部服务。

自动化越顺畅，越容易让人忘记它正在接触什么数据。把测试环境与真实环境隔离，是使用这类功能的前提，不是可选优化。

## 这次更新真正改变的是什么

iPhone Duo 只是一个具体设备，更重要的变化是 AI 编程工具开始拥有“观察结果”的能力。

过去我们把一段错误描述给 Claude，它根据文字猜测；现在它可以运行应用、改变屏幕形态、看到问题，再回到代码寻找原因。这个闭环仍需要人来定义目标、批准修改和判断体验，但它已经比单纯生成代码可靠得多。

最好的使用方式不是说“帮我适配折叠屏”，而是把测试范围、操作步骤、验收标准和隐私边界写清楚，让 Claude 承担重复操作，人来决定什么才算好用。
